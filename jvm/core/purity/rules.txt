# What core source (jvm/core/*/src/main) may not use. Read by PurityCheck.java; every :core-* module's `check` runs it.
#
#   rule <id> <reason>              one per rule: why the core may not use it (printed with every finding)
#   <id> classpath <glob>           a dependency on the module's compile or runtime classpath ("group:name:version" or
#                                   "project :name"); * matches anything
#   <id> class <internal name>      any reference to the class (and its nested classes) in compiled code: calls, fields,
#                                   types, casts, signatures; a name ending in / is a package and its sub-packages
#   <id> member <glob>              a call or field use, matched as owner.name(descriptor)type, e.g.
#                                   java/lang/Double.toString(D)Ljava/lang/String;  (* matches anything)
#   <id> concat <descriptor>        a string concatenation (javac's invokedynamic) with an operand of this type
#   <id> source <regex>             a match in the source text, comments and string literals removed
#   <id> op <OPCODE>                a bytecode arithmetic or conversion instruction (D2F, FADD, DREM...), found in
#                                   compiled code; what the source says does not matter, only what javac made of it
#
# An exception is a line in allow.txt beside this file: the file, the rule, and why, argued in the open.

rule float-narrow The web compile's JavaScript target does not narrow a float: a cast from double, float + - * / and an int or long converted to float all stay doubles there (0.1 stays 0.1, 16777217 stays exact), where the JVM and the WebAssembly target round to single precision; a float field, local, parameter, return, record component or boxed Float then carries the wrong number. Literals, float[] stores and Float.floatToIntBits narrow on every target. Round at the point of the narrowing through core-base's Float32Ops (of(double) for a cast, add, sub, mul and div for the four operations, of(int) and of(long) for a conversion), which narrows on every target; or keep the value a double.
float-narrow op D2F
float-narrow op I2F
float-narrow op L2F
float-narrow op FADD
float-narrow op FSUB
float-narrow op FMUL
float-narrow op FDIV

rule remainder The web compile's WebAssembly GC target computes % on a double or float as x - trunc(x / y) * y, which is not the exact remainder: 123456.789 % 0.001 gives 0 (the JVM and JavaScript give 1.7374062258324052e-12), 3.4028236e38 % 2 gives 3.4028236e38 (not 0), -0.1 % 0.1 gives 0 (not -0), and 0 % -0 gives 0 (not NaN). Use core-base's JsMath.rem, the exact remainder (fmod) on every target. An int or long % is exact everywhere and is not flagged.
remainder op DREM
remainder op FREM

rule math-exact The JVM's Math replaces sin, cos, tan, log, log10, exp, pow (and on newer JDKs tanh and cbrt) with processor-specific code that can differ from StrictMath in the last place, so an answer would depend on the player's JDK and processor; the web compile's Math is the browser's (other algorithms: pow and exp a place off) or its own shortcuts (cbrt(262144) is 63.999999999999986, rint and round move halves the wrong way, rint(1e300) is garbage, tanh(800) is NaN, log10(1000) is 2.9999999999999996, log1p and expm1 lose small arguments). Call core-base's ExactMath, fdlibm in plain Java: StrictMath's bits on the JVM and on both web targets.

# 0.2.0-beta.3-tux.2: under the hood

The second fork release, cut from the joined repository. Base version 0.2.0-beta.3; tag `mod-0.2.0-beta.3-tux.2`.
The same jar goes on the server and on every client.

## What changed

- View-only cards: a website card the game cannot run is a board node with `Node.shown` (core-model `Shown`:
  plan id, reason OFF, KIND, MISSING or ABSENT, solved or not, first place). Its plan card and recipe stay in the
  graph's site and are written back whole by core-codec `DisplayCards.site`. A card the board moved goes out at its
  board place, and a deleted one goes with its recipe and kept wires. The importer, the cloud reader and the save all
  make these cards through one maker (`ShownCards.show`). Saves keep them under `site`, `siteWhy`, `siteAt` and
  `siteIn`. A tux.1 save's site cards are shown when it is read.
- Solve: a solved view-only card is a 20-tick machine of its ports' per-second amounts at the plan's count and rule.
  An unsolved one is in the input at count 0, so every node has an answer.
- A file import moves the plan to the board's corner. A view-only card now counts as unmoved only while the board
  has it at the plan's own place. Otherwise, it goes out at its board place with everything around it
  (`PlanRoundTripTest.anImportedPlanGoesBackWithEverythingWhereItWasToEverythingElse`).
- Cloud: `PlanRead` and `PlanWrite` carry view-only cards. A move or delete is a live op. The merge drops a card
  the cloud copy no longer has, with its wires, whichever order the race takes. `PlanWrite.meta` merges
  `settingPins` and `spareShares` by key. A drawer's `drainMode` comes back through `SiteCarry`.
- Special cards from shared records (core-view `core.view.special`). The custom rate card, the fluid tank and
  generator cards draw their name, chips, count line and strip from `SpecialViews`, the same rules the website uses.
  Generator readings cross as `reading:<label>` under `power:<source>` in `settingPins`, both ways.
- Rails: a free input (the Rock Breaker's lava) is marked by the shared `FreeInputs` rule that the website's rail
  rows read.
- Wire contract (`conformance/wire/`): the mod's client is tested against the same request and answer data as the
  website's routes and live service. Fixed on the client side:
  - `/me` carries no account id. The id now comes from the session token.
  - A live close with 4001 (auth) is not retried.
  - Nearby accounts are read as `{id, username}`.
  - The site's error text on a 401 to a request with a body is kept: requests no longer use fixed-length streaming.

## For the server operator

The jar names no remote host. Everything it may contact comes from the `network` category of
`config/gtnhplanner.cfg`. Every key is empty in a fresh install, and empty switches the feature off. A fresh jar
writes this block:

```
network {
    S:headerName=
    S:headerValue=
    S:liveUrl=
    S:siteUrl=
    S:supportUrl=
    S:updateUrl=
    S:websiteOrigins <
     >
}
```

- `siteUrl`: the website, `http://` or `https://` and a host. It turns on the community library, accounts and
  posting, bug reports, cloud plans and plan links.
- `liveUrl`: the live service, `ws://` or `wss://` ending in `/live`. Empty derives it from `siteUrl`.
- `updateUrl`: an address that answers with a release list in GitHub's releases JSON. Tags may be `mod-<version>` or
  `<version>`. `-tux.N` orders after its base version and before the next one. Anything else (`web-*` tags) is
  skipped. Empty: no update check. The update check never sends the header below.
- `supportUrl`: a help page the Feedback box links to. Empty hides the link.
- `websiteOrigins`: one origin a line, besides the site's own, allowed to send plans with Open in the mod.
- `headerName` and `headerValue` (new): one extra header, for a site behind a guarding reverse proxy that lets a
  request through only with a pre-shared header. With both set, it goes on every request to `siteUrl` and to the
  live service (the library, accounts, posting, bug reports, cloud plans, the `/live` WebSocket upgrade), and to no
  other host. For example:

```
network {
    S:headerName=X-Access-Key
    S:headerValue=<the value the site's owner gives out>
    S:siteUrl=https://planner.example.org
}
```

- The value is a shared secret of the pack, not a per-user credential: every player's config file holds the same
  value in plain text. Anyone with a copy of the pack's config has it. Rotate it on the proxy and in the pack's config
  together.
- Set it in the config file, not with `-Dgtnhplanner.header.value`. Minecraft prints its JVM flags in every crash
  report. The system properties `-Dgtnhplanner.header.name` and `-Dgtnhplanner.header.value` still win over the file,
  as the other `-Dgtnhplanner.*` properties do.
- Both empty (the default) sends nothing. A setting that turns the header off, with one warning in the log naming the
  key (never the value):
  - one key set without the other;
  - a name that is not a header token;
  - a name the client sets itself (`Cookie`, `Host`, `Content-Length`, `Content-Type`, `Transfer-Encoding`,
    `Upgrade`, `User-Agent`, `Origin`, any `Sec-WebSocket-*` or `Proxy-*`, and the rest of the list in
    `conformance/wire/README.md`);
  - a value with a control or non-ASCII character.
- The mod never follows a redirect. When the site answers with one (the header missing or wrong), the player sees
  "The site asked for a sign-in the mod cannot do", and cloud plans stay on this computer. A wrong value behaves like
  no header.
- The value is never written to a log, an exception or the debug overlay.

The mod works on the client. On a dedicated server it loads, writes its config and does nothing else, and installing
it there is optional. If it is installed there, give the server the same jar as the clients.

## Checked in a game

Dev client (GregTech set, Java 25), on the commit the tag goes on unless said:

- Cards from NEI's Smelting, Shaped Crafting and Bending Machine pages, wires, a product drawer at 1/s: 30 furnaces and
  8.4 LV benders for 3 plates a second. Arrange, and a world saved by the previous build reloads with every card,
  count, drawer and wire as it was.
- A website plan with an ore vein, a Thaumcraft infusion, a switched-off card and a card with no recipe: each shows
  VIEW ONLY with its reason, the vein solved at its Exactly 2. Moved one, deleted two, exported: the moved card at its
  new place, the deleted ones gone with their wires, the untouched one at its board place beside its neighbours.
- No site set: a logging proxy and a socket sampler saw no connection from the planner, and only the dev harness
  listens.
- A local stand-in site behind a header (on the commit before the generator cards; the network code is the same):
  - No header, a name without a value (one warning in the log) and a wrong value: the Community tab, account creation
    and Feedback each say the site asked for a sign-in the mod cannot do, with no retry and no repeated request.
  - The right value: account creation, posting, cloud plans up, a view-only card moved and deleted through the live
    room, a card deleted on the site's side leaving the board with its wire, the live room with a second person, and
    the nearby player in Plan together.
  - A live close 4001 after the site forgot the session: one warning, no reconnect in the next minute.
  - A wrong password shows "Wrong username or password.".
  - The value appears in no file of the run directory but `config/gtnhplanner.cfg`, and not on the F3 screen.

## Known differences

- A tux.1 save of a website plan imported from a file shows its website-only cards at the plan's own place. That
  save's other cards were moved to the board's corner on import, and the save did not keep by how much, so those
  cards can stand apart from the rest. Moving one puts it right from then on.
- The Overview's machine rows show a count box for a view-only card. Typing a count there does nothing.
